# 性能优化建议（第二轮）

> 范围：当前 `main`（提交 `d76d348`）之后的代码。
> 已落地：连接池、好友/测验去 N+1、索引、列表分页、时间统一。
> 本文只列**剩余**可优化点，按「收益 / 成本」排序。

---

## 一、P0：同步 DB 调用写在 `async def` 里，阻塞整个事件循环（收益最大）

### 现状
所有路由都是 `async def`，但内部用同步 `psycopg2`（`db_cursor`）访问数据库，例如：
- `services/api/app/modules/auth/router.py` 全部 `async def`
- `services/api/app/modules/moments/router.py`、`chat/router.py`、`quiz/router.py`、`admin/router.py` 同样
- `server.py` 用单进程 `uvicorn.run(...)`（无 workers）

### 影响
`async def` 路径函数直接在事件循环里执行；同步 DB I/O（含 Neon 网络往返，几十~几百 ms）会把**整个进程**卡住，其它请求（包括别的 WebSocket 消息）只能排队。等于并发度接近 1，连接池开多大都用不上。

### 方案（低成本、收益高）
把纯 DB 型接口从 `async def` 改成普通 `def`，FastAPI 会自动放到线程池执行：

```python
# 之前
@router.get("/moments")
async def get_all_moments(...): ...

# 之后（去掉 async 即可）
@router.get("/moments")
def get_all_moments(...): ...
```

- WebSocket 端点必须保持 `async def`，把其中的同步 DB 调用用 `starlette.concurrency.run_in_threadpool(...)` 包一层。
- 线程池默认 40，连接池上限（`DB_POOL_MAX_CONN`）需与之匹配（建议 20~40），注意 Neon 连接数上限。
- 彻底方案：改用 `asyncpg` + async SQL（成本高，可后置）。

### 预期
单实例并发吞吐提升数倍到十几倍，尤其在慢查询/Neon 冷启动时最明显。

## 二、P0/P1：搜索接口 `ILIKE '%q%'` 无法走索引（全表扫描）

### 现状
`services/api/app/modules/search/router.py`：
```sql
WHERE (u.username ILIKE %s OR u.nickname ILIKE %s) ...
```
前后通配符的 `ILIKE` 无法用普通 B-Tree 索引，用户表一大就是全表扫描。

### 方案
启用 `pg_trgm` 扩展并加 GIN 索引（幂等，可加到 `db.py` 的 `SCHEMA_STATEMENTS`）：
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX IF NOT EXISTS idx_users_username_trgm ON users USING gin (username gin_trgm_ops);
CREATE INDEX IF NOT EXISTS idx_users_nickname_trgm ON users USING gin (nickname gin_trgm_ops);
```
> Neon 支持 `pg_trgm`；若托管方限制扩展，退化为「前缀匹配 `q%`」或加 `username` 精确/前缀索引。

### 预期
搜索从 O(N) 全表扫降到索引扫描，用户量大时数量级提升。

## 三、P1：后台「用户监控」用相关子查询，且无分页

### 现状
`services/api/app/modules/admin/router.py` 的 `/admin/users`：
```sql
SELECT ..., 
  (SELECT COUNT(*) FROM moments WHERE username = u.username),
  (SELECT COUNT(*) FROM drive_records WHERE username = u.username),
  (SELECT COUNT(*) FROM quiz_attempts WHERE respondent_username = u.username)
FROM users u ORDER BY u.created_at DESC
```
每个用户跑 3 个子查询（本质 N+1），且一次性返回全量用户。

### 方案
改为一次 `LEFT JOIN + GROUP BY` 聚合，并加 `limit/offset`：
```sql
SELECT u.id, u.username, COALESCE(u.nickname,u.username), COALESCE(u.avatar_url,'👤'), u.created_at,
       COUNT(DISTINCT m.id) AS posts_count,
       COUNT(DISTINCT d.id) AS drive_count,
       COUNT(DISTINCT qa.id) AS attempts_count
FROM users u
LEFT JOIN moments m ON m.username = u.username
LEFT JOIN drive_records d ON d.username = u.username
LEFT JOIN quiz_attempts qa ON qa.respondent_username = u.username
GROUP BY u.id
ORDER BY u.created_at DESC
LIMIT %s OFFSET %s
```
（大表可拆成 3 个 `GROUP BY` 子查询再 JOIN，避免笛卡尔放大。）

## 四、P1：聊天历史无上限，且每次打开都写库

### 现状
`chat/router.py::get_chat_history` 每次打开会话：
1. `UPDATE ... SET is_read=TRUE`（即使没有未读也写一次）；
2. `SELECT` 返回**全部**历史（无 LIMIT），长期会话可能上万条。

### 方案
- `SELECT ... ORDER BY created_at DESC LIMIT 200` 后再反转（或 `LIMIT %s OFFSET %s` 分页）；
- 先 `SELECT COUNT(*) ... AND is_read=FALSE`，有未读才 `UPDATE`；
- 历史查询的 `OR` 条件可拆成两条 `UNION ALL`，更好利用 `(sender,receiver)` 索引。

## 五、P1：缺少响应压缩与缓存

- **压缩**：API 多数字段是 JSON，给 FastAPI 加 `GZipMiddleware`（`minimum_size=1024`）可显著减小动态/列表响应体积。
- **缓存**：`GET /moments`（推荐流）、`GET /anime/*`（静态数据）适合短 TTL 缓存。依赖里已装 `redis` 但未使用，可接入；静态动漫数据其实放前端即可，省一次往返。
- **HTTP 缓存**：列表接口可加 `ETag` / `Cache-Control`，配合前端已有 localStorage 做 SWR。

## 六、P2：前端性能

1. **路由懒加载不彻底**：`apps/web/src/router/index.js` 里 Home/Search/Chat/Notifications/Quiz/Auth/Anime 都是静态 import，只有 QuizDesign、Drive 是动态 import。首屏会把所有页面打进主包（~160KB）。建议全部改 `() => import(...)`，配合 `<Suspense>`。
2. **`vite-plugin-vue-devtools` 无条件挂载**：`apps/web/vite.config.js`、`apps/admin/vite.config.js` 里插件未按环境判断，建议 `mode === 'development'` 才启用，避免任何生产副作用。
3. **每条消息新建 `AudioContext`**：`apps/web/src/store/chat.js::playNotificationSound` 每次提示音都 `new AudioContext()`，频繁创建会触达浏览器上限并占用资源。应复用单例并在首次交互后 `resume()`。
4. **`v-for` 用索引当 key**：`ChatView.vue` 消息列表 `:key="idx"`，消息增删（撤回）时整段重渲染；应改为 `:key="msg.id || msg.client_id"`。
5. **localStorage 全量写入**：每次收发消息 `writeJSON('cached_history', ...)` 都会序列化整个缓存对象，高频聊天时是同步阻塞。建议防抖/`requestIdleCallback` 写入，或只存最近会话。
6. **轮询频率**：`HomeView` 每 15s 查一次新动态、`chat` 每 20s 查好友请求。用户多时后端压力大，可改 SSE/WebSocket 推送或提高间隔。

## 七、P2：数据库与部署层

1. **Neon 连接串用 pooled endpoint**：若直连 `...-pooler...` 之外的主机，每次建连成本高；建议用 Neon 的 pooled 连接串（pgbouncer），与进程内连接池叠加使用。
2. **设置语句超时**：建连时加 `options='-c statement_timeout=15000'`，防止慢查询长期占用连接。
3. **多 worker 与连接数换算**：若 `uvicorn --workers N`，总连接 = `N × DB_POOL_MAX_CONN`，需对齐 Neon 上限。
4. **R2 上传流式化**：现在是 `await file.read()` 全量读入内存（已限 5MB），可改 `r2_client.upload_fileobj` 流式上传，降低内存峰值。
5. **建表 DDL 每次启动都跑**：`init_global_tables` 每次开机执行全部 DDL；可加一个版本标记表，仅在版本变化时迁移，缩短冷启动。

## 八、实施状态（已全部落地）

- ✅ **并发模型**：所有 DB 型接口由 `async def` 改为同步 `def`（FastAPI 线程池执行）；WebSocket 内消息落库/已读/撤回改 `run_in_threadpool`，不再阻塞事件循环。连接池上限默认 20，并加 `statement_timeout=15s`、`connect_timeout=10s`。
- ✅ **搜索索引**：启动时创建 `pg_trgm` 扩展与 `users.username/nickname` GIN 索引（扩展不可用时打印告警并降级）。
- ✅ **后台用户列表**：`/admin/users` 改为 3 个聚合子查询 + `LEFT JOIN`，并支持 `limit/offset` 与 `total`。
- ✅ **聊天历史**：改为 `UNION ALL` 双索引查询 + 最近 N 条限制（默认 200）、仅在存在未读时写库。
- ✅ **上传**：R2 改为 `upload_fileobj` 流式上传（先探测大小与魔数，再流式发送）。
- ✅ **响应压缩**：新增 `GZipMiddleware`（>1KB 压缩）。
- ✅ **前端路由**：全部路由懒加载（web 主包由 ~160KB 降至 ~124KB，各页面独立 chunk）。
- ✅ **前端构建**：`vite-plugin-vue-devtools` 仅开发模式启用。
- ✅ **前端运行**：提示音 `AudioContext` 单例；消息列表 `key` 改用 `id/client_id`；localStorage 写入 300ms 防抖；轮询在页面不可见时跳过。
- ✅ **asyncpg 全异步改造**：后端数据层已由 psycopg2 同步驱动整体迁移到 asyncpg（异步连接池、事务上下文、JSONB codec、`$n` 占位符），WebSocket 路径不再需要线程池桥接。
- 🚫 未做（需额外基础设施/权衡）：Redis 响应缓存（当前未部署 Redis，接入需配置实例）、DDL 版本化（当前幂等 DDL 开销极小）。
